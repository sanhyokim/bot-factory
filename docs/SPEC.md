## 0. 用語(初出の定義)

| 用語 | 意味 |
|---|---|
| BOT | 決められた売買ルールで自動で注文を出す小さなプログラム。本書では1本ごとに記号(例: B-0031)で呼ぶ |
| 案 | 「こういう場面で売買すれば儲かるかもしれない」という仮説。BOTになる前の状態 |
| 工場 | 案を出し、ふるいにかけ、合格したBOTだけ本番に出す一連の自動の流れ。本システム全体のこと |
| 工程 | 工場の中の段階。探索・調査・新ロジック開発・実装・paper評価・反証・修理・本番の8つ |
| 型 | 売買ルールの種類。**値動き型**(これから上がる/下がるを当てて差で稼ぐ)と**歪み型**(今この瞬間、あるべき値段からずれている分が戻るのを取る)の2つ |
| paper評価(試運転) | お金を使わず、「もし動かしていたら」の損益だけを記録する試し運転 |
| 反証 | paper評価に合格したBOTを、別の角度から「本当に効いているか」を疑って検査する工程 |
| 否決メモ | 落ちた案・BOTについて「どの工程で・なぜ落ちたか」を定型で残す帳簿。本システムの要 |
| 札(タグ) | 否決メモに付ける分類ラベル。集計できるように、決まった語だけ使う |
| 関所 | ボスの判断を待って止まる場所。本番昇格(関所1)と本番再開(関所2)の2か所 |
| Hyperliquid | 本システムが取引する暗号資産の取引所。無期限先物(期限のない先物)を扱う。取引記録が全員分公開されている |
| 財布(ウォレット) | Hyperliquid上の口座にあたるもの。住所(アドレス)という文字列で識別する |
| 順位表 | Hyperliquidが公開している、成績上位の財布の一覧 |
| 資金調達料 | 無期限先物を持ち続ける人が1時間ごとに払う(または受け取る)手数料。買い手が多いと買い手が払い、売り手が多いと売り手が払う |
| 手数料 | 注文1回ごとに取引所に払う費用 |
| 滑り | 注文が思った値段で通らない分。本書では往復0.05%の固定値 |
| 足 | 判断に使うローソク足1本。「始値」はその足が始まった時の値段、「終値」は終わった時の値段 |
| AI窓口 | 工場の中でAIに質問を送る唯一の口。設定を変えるだけで、使うAI(Claude Code / API)を切り替えられる |
| API | 使った分だけ払う方式でAIを呼ぶ接続口。Claude Code(Max契約)とは別の口座 |
| Haiku / Sonnet / Opus | Claude(AI)の3段階。Haikuが最も安く速い、Opusが最も高く賢い、Sonnetは中間 |
| レバレッジ | 手持ち資金より大きな金額で取引する仕組み。本システムは**1倍固定**(使わない) |
| ダッシュボード | 工場の状態を見る画面。手元のパソコンのブラウザで開く |
| 見張り役 | 工場の各部分が止まっていないかを監視し、止まっていたら再起動する小さなプログラム |

## 1. 目的と方針

### 1.1 目的
「儲かる可能性が高いBOTを、人手をかけずに探し続ける工場」を自分の手元に持つこと。

### 1.2 「儲かる」の定義(ボスの見解を採用)
検証(paper評価と反証)に合格し、**本番で実際に利益が出た結果**だけを「儲かった」と呼ぶ。試運転の数字や推定は「儲かりそう」であり、「儲かった」ではない。

### 1.3 最初の目標(利益ではない)
最初の2〜3か月の目標は次の3つ。本番の利益はこの期間の目標に含めない。
1. 工場が毎日、人手なしで一周する(探索から反証まで自動で進む)
2. 否決メモが育ち、同じ理由で落ちる案が減っていることが数字で見える
3. 本番昇格の候補が、ボスの前に定期的に(週に数件以内で)届く

### 1.4 参考にした著者(あいかわひびき氏)の方式との違い
参考にしたのは「AIにBOTを量産させ、試運転で選別し、本番に出す」という工場の形、否決の経験を書き残して次に読ませる考え方、「もう稼いでいる誰かの動きを見て学ぶ」探し方、「BOT同士で共通部品を作らず1本ずつ捨てやすくする」作り方。本システムで変えた点は次の5つ。
1. 否決メモに札を付け、集計できる帳簿にする(著者は2,500ページの読み物)
2. 新しい案を登録する前に否決メモと照合し、同じ理由で落ちた案は出さない
3. 探索の入口に「儲けている財布の分析」を正式な工程として置く
4. BOTごとにかかったAI代を帳簿に付け、利益と並べる
5. 「反証」を正式な工程にする

### 1.5 型の扱い
著者は「値上がりを当てにいく売買はしていない」(歪み型のみ)。本システムは**値動き型と歪み型の両方**を扱う。工場の仕事は「案を検証し、手数料を引いた純利益で合否を決める」だけなので、型が違っても同じ合格条件で判定する。型によって変わるのは、売買ルールの定型(4.2)と、否決メモの集計の分け方(6.3)だけ。

### 1.6 人間(ボス)に必ず上げること
次の3つは自動化せず、必ずボスが行う。
1. お金を入れる(本番資金の投入・段階の繰り上げ)
2. 鍵を渡す(APIキー・取引所の注文用の鍵)
3. 有料契約をする(AIの追加課金、有料のデータ窓口、サーバー)

### 1.7 やらないこと(禁止)
- BOT・コード・シグナルを他人に売る、貸す、配信する
- 他人の資金を預かって運用する
- レバレッジを使う(常に1倍)
- 記事の文章・画像を転載する
(理由: 自分の資金で自分用に動かす限り、著作権・取引所規約・金融の法律のいずれにも触れない。売る・貸す・預かる・配信するは金融商品取引業の登録対象で、無登録は刑事罰。本書の範囲外とする)

### 1.8 二段構えの方針(2026-10-20・ボス承認)
著者の2026-10-20の性能分析(本人公開)から、次が分かった。
- 稼ぎの約3分の2は「清算」(借金の担保が足りなくなった口座を強制的に処分して報酬を受け取る仕事)。本番66本中62本が黒字
- 「一回きりの機会(取ったら終わり)」が稼ぎの半分。「常にある機会」は93本試して黒字17本と低い
- 競争相手がいない機会の歩留まり66%、いる機会は27%。古い・放置された仕組みに残った残高を拾っている
- 本番に出したBOTは8〜9割が黒字(厳しい試運転の関所が効いている)
- 安い無料のAIに替えたら、作業から本番への歩留まりが12%→5%に落ちた

本システムの値動き型・歪み型は、どちらも「常にある機会」側で、歩留まりが低い側に当たる。よって方針は二段構えとする。
1. **工場はHyperliquidで完成させる**(段階3b→4)。工場と否決メモは、どの稼ぎ方にも使い回せる土台
2. **稼ぎはチェーン上の一回きりの機会で取りに行く**(段階5)。最初は1チェーン(HyperEVM)の貸し借りの仕組みで、担保不足の口座を処分する「清算」から始める

Hyperliquidの先物取引の中では清算はできない(取引所自身が処理する)ため、段階5は別のチェーンへの接続が必要になる。詳細は段階4の後に仕様化する。

## 2. 全体像

### 2.1 工程の流れ

```
探索(財布分析 / 資金調達料の歪み) → 調査 → 新ロジック開発 → 実装 → paper評価 → 反証 → [関所1: 本番昇格] → 本番運用 → (自動停止) → [関所2: 再開]
                                                      ↑         ↓(不具合)
                                                      └── 修理 ──┘
各工程で落ちたものは → 否決メモ へ
```

たとえ: 包丁工場。「名人の包丁を1本盗む」のではなく「毎日たくさん作って、試食会と検査に通ったものだけ店に出す」。ボスが押すのは「出荷の判子(関所1)」と「ライン再開の判子(関所2)」だけ。

### 2.2 各工程の役目(1行ずつ)

| 工程 | 役目 | 使うAI |
|---|---|---|
| 探索 | (入口1)儲けている財布を見つけ、取引の癖から案を出す。(入口2)資金調達料が極端な銘柄を見つけて案にする | Haiku(入口1のみ。入口2は計算だけ) |
| 調査 | 案が「手数料で消えないか」「機会は足りるか」「資金で足りるか」を調べて見送り/継続を決める | Haiku(見送り理由の言い換えのみ) |
| 新ロジック開発 | 案を、数字で書いた売買ルールに落とす | Sonnet |
| 実装 | 売買ルールからBOTのコードとテストを書く | Sonnet |
| paper評価 | 14日以上・30回以上の試運転で成績を記録し、合格条件で判定 | AI不要(計算のみ) |
| 反証 | 合格したBOTを「たまたまではないか」の3条件で検査 | Sonnet(判定の説明文のみ) |
| 修理 | 実装不良・軽い不具合を直す。3回で直らなければ落とす | Sonnet |
| 本番運用 | 本番資金で動かす。停止条件で自動停止 | AI不要 |

### 2.3 案の残り方の目安(100件あたり・推定)

| 工程 | 残る数 |
|---|---|
| 探索で案登録 | 100 |
| 調査を通過 | 30〜40 |
| 実装まで進む | 15〜20 |
| paper評価を完走 | 10〜15 |
| 反証を通過 | 3〜5 |
| 本番昇格 | 1〜10 |

最初は1%、否決メモが育てば10%が目安。これは目標であり、合格条件を緩めて達成してはならない。

### 3.3 見張り役(止まらない工夫)
著者はメモリ枯れで丸一日以上止まった。本システムは次を入れる。
- 工場の各部分(価格の受け取り口、paper評価、本番運用、画面)は別々のプロセスで動かす
- 見張り役が1分ごとに各プロセスの生死とメモリ使用量を確認する
- メモリが上限(初期値: 1プロセスあたり1GB)を超えたら、そのプロセスだけ再起動する
- プロセスが落ちていたら再起動する。1時間に3回以上落ちたら再起動をやめ、ダッシュボードの「要判断」に出す
- ログは `data/logs/` に、プロセスごとではなく**1か所**に日付ごとのファイルで集める。画面から日付と工程で引ける
- 再起動の記録は否決メモではなく、ログと画面(枠6)に残す

## 4. データ(帳簿)

すべて `data/factory.db` に保存する。日時はすべて日本時間で記録する。

### 4.1 案(ideas)
| 項目 | 内容 |
|---|---|
| 案ID | 例 `I-00041`。連番 |
| 作成日時 | |
| 出どころ | `wallet`(入口1: 財布分析)/ `funding`(入口2: 資金調達料の歪み) |
| 型 | `値動き` / `歪み` |
| 元の財布 | 財布分析の場合、その住所 |
| 要約 | 1〜2文。「どの銘柄で、どんな場面で入り、どう出るか」 |
| 仮説の本文 | AIが書いた仮説(300字以内)。入口2はプログラムが定型文で書く |
| 入る条件の種類 | 6.3の照合キー(7語)のどれか |
| 現在の工程 | 探索/調査/新ロジック開発/実装/paper評価/反証/修理/本番/否決 |
| 現在の判定 | 待機/継続/保留/見送り/完了/未対応 など(工程ごとに定義。5章) |
| 照合結果 | 登録前照合で似た否決メモがあったか(あり/なし)と、あった場合のメモID |

### 4.2 売買ルール(rules)
案ごとに1つ。新ロジック開発工程が作る。**定型以外の項目は増やさない**(シンプルで確実を優先)。型によって定型が違う。

**共通の項目**
| 項目 | 内容 |
|---|---|
| ルールID | 案IDに対応 |
| 型 | `値動き` / `歪み` |
| 銘柄 | 1つ(例: BTC、ETH、HYPE) |
| 1回の上限額 | ドル。paper評価は200ドル、本番は資金段階に従う |
| 同時に持てる数 | 1(固定) |
| レバレッジ | 1倍(固定・変更不可) |
| 1日の最大取引回数 | 数字 |
| 損切り | 入った値段から何%逆に動いたら出るか(例: −0.8%)。両型で必須 |

**値動き型だけの項目**
| 項目 | 内容 |
|---|---|
| 時間の単位 | 判断に使う足の長さ(例: 5分、15分、1時間) |
| 入る条件 | 数字で書く(例: 「直近20本の高値を上に抜けたら買う」)。入る条件の種類は7語のどれか |
| 出る条件 | 利益確定を数字で(例: 「+1.5%で確定」)。保有の上限時間も数字で |

**歪み型だけの項目**
| 項目 | 内容 |
|---|---|
| 歪みの対象 | 本書では `資金調達料` のみ(将来、他の歪みを足す時はボスの承認) |
| 入る条件 | 「1時間あたりの資金調達料が +x% 以上(買い手が払いすぎ)なら売りで入る/ −x% 以下(売り手が払いすぎ)なら買いで入る」の x を数字で |
| 出る条件 | 「資金調達料が ±y% の内側に戻ったら出る」の y と、「最長 N 時間で必ず出る」の N を数字で |

歪み型の考え方: 資金調達料を**受け取る側**で入り、受け取りを積み重ねる。利益の源泉は値動きではなく受け取り。危険は、持っている間に値段が逆に動くことなので、損切りと最長保有時間で守る。

## 5. 工程ごとの仕様

各工程は「入口(何を受け取るか)→処理→出口(どこへ送るか)→判定(どの札か)」で書く。

### 5.1 探索

**入口**: なし(毎日自動で始まる)。入口1と入口2を毎日両方行う。

#### 入口1: 財布分析(値動き型の案を出す)
1. Hyperliquidの順位表から、直近30日の成績上位の財布を最大300件取る(AI不要)
2. 各財布の直近30日の取引履歴を、1件ずつ読み取り窓口で取る(AI不要)
3. 次の条件で絞る(AI不要):
   - 取引回数が30日で50回以上(「入ってから出るまで」を1回と数える)
   - 30日の純利益がプラス
   - 最大の落ち込み(一時的に資金が減った最大幅)が20%以内。確定した損益の資金曲線で計り、30日前の資金は「今の資金 − 30日の損益」で推定する
   - **独自条件**: 1回あたりの取引額の中央値が2,000ドル以下(資金50〜500ドルで真似できる取引をしている人を優先)
   - 約定が30日で6,000件を超える財布(超高速の取引)は対象外
4. 絞った財布は最大30件。各財布について、**ここで初めてAI(Haiku)**に次を頼む:
   「この財布の直近100件の取引(銘柄・入った時刻と価格・出た時刻と価格)を読み、どんな場面で入り、どんな場面で出ているかの仮説を3つ、各300字以内で書け。銘柄・時間の単位・入る条件・出る条件を必ず含め、入る条件の種類を7語(高値抜け/安値割れ/平均回帰/急落/急騰/出来高急増/資金調達料)から1つ選ぶこと。どれにも当てはまらなければ『分類できない』と答えること」
5. 「分類できない」と答えた仮説は案にしない。否決メモに札 `ルール不成立`、一言の理由「入る条件の種類を分類できず」で残す
6. 残った仮説を**登録前照合**にかける(6.3)。似た否決メモがあれば登録しない
7. 残った仮説を案として登録(型 `値動き`、出どころ `wallet`、判定: 案登録)
8. 調べた財布は、絞り込みに落ちたものも含めて7日間は再分析しない

#### 入口2: 資金調達料の歪み(歪み型の案を出す)※段階3bで追加
1. Hyperliquidの全銘柄について、直近24時間の資金調達料(1時間ごと)を取る(AI不要)
2. 次の条件で絞る(AI不要):
   - 直近24時間のうち、1時間あたりの資金調達料の絶対値が **0.01%**(年率換算で約88%)を超えた時間が **3時間以上**ある銘柄
   - 直近24時間の出来高が **100万ドル以上**(薄い銘柄は滑りが大きいため除外)
3. 絞った銘柄ごとに、プログラムが定型で案を1つ作る(AI不要):
   - 要約「{銘柄}の資金調達料が極端(直近24時間の最大 {値}%/時)。受け取る側で入り、戻ったら出る」
   - 入る条件の種類は `資金調達料`
4. 登録前照合にかける(6.3。型 `歪み` の否決メモとだけ照合)
5. 残った案を登録(型 `歪み`、出どころ `funding`、判定: 案登録)
6. 同じ銘柄は3日間は再登録しない

**出口**: 調査工程へ

**判定の札**: `案登録` / `照合で除外`(札 `重複`)/ `ルール不成立`(分類できず)

**費用の上限**: 1日あたりHaikuの入力500万文字分まで。超えたらその日は打ち切り。入口2はAIを使わない

### 5.2 調査

**入口**: 案登録された案

**処理**(数字の計算はプログラム。AIはHaikuで「見送りの理由の文章化」だけ。プログラムが数字入りで先に書き、Haikuが一括処理で言い換えて差し替える):

**値動き型**
1. 想定の値幅(利益確定の%)が、往復の手数料+滑りの**3倍未満**なら見送り(札 `手数料負け`)。基準は 3 ×(0.045% × 2 + 0.05%)= 0.42%
2. その銘柄の直近30日で、入る条件が成り立ち始めた回数が**10回未満**なら見送り(札 `機会不足`)。1分足・5分足は取引所から30日分が取れないので、取れた日数から30日分に換算する
3. 必要資金が200ドルを超える条件(最小注文単位が大きい銘柄)なら見送り(札 `資金不足`)
4. 入る条件の種類が7語でない案は否決(札 `ルール不成立`)

**歪み型**
1. 直近30日で、1時間あたりの資金調達料の絶対値が入る条件の x% を超えた時間が**30時間未満**なら見送り(札 `機会不足`)
2. 直近30日のそれらの時間について、「受け取れた資金調達料の合計」が「往復の手数料+滑り(0.14%相当)の合計」の**2倍未満**なら見送り(札 `手数料負け`)。受け取りは「超えた時間に持っていたとして」の単純な合計で計算する
3. 必要資金の検査は値動き型と同じ

**共通**: 上記を通ったら継続

**出口**: 新ロジック開発へ

**判定**: `継続` / `見送り` / `保留`(外部データが取れなかった時。翌日再試行、3回で `未対応` として否決)

**1日の上限**: 90件

### 5.3 新ロジック開発

**入口**: 調査を通った案

**処理**(AI: Sonnet):
1. 否決メモから、この案と**同じ型・同じ銘柄・同じ出どころ**で落ちたメモを最大5件取り、「過去にこの理由で落ちている」としてAIに渡す(6.3の用途2)
2. AIに、4.2の定型(型に応じた項目)に沿った売買ルールを**1つだけ**書かせる。定型にない項目は書かせない
3. 定型の全項目が数字で埋まっているかをプログラムで検査。欠けていれば1回だけ書き直し。それでも欠ければ否決(札 `ルール不成立`)
4. 歪み型は、入る条件の x を「調査で見つかった直近30日の最大値の半分」から始めさせる(AIが勝手に大きくしない)

**出口**: 実装へ

**判定**: `完了` / `保留`(書き直し待ち)

**1日の上限**: 10件

### 5.4 実装

**入口**: 売買ルール

**処理**(AI: Sonnet):
1. 土台(`bots/_template/`)を `bots/{BOT記号}/` に**コピー**し、売買ルールの「入る条件」「出る条件」の部分だけをAIに書かせる。注文・記録・停止・損切り・最長保有の部分は土台で固定し、AIに触らせない
2. **BOTは1本ずつ自己完結**とする。土台を後で更新しても、既にコピーされたBOTには反映しない(1か所直すと全部壊れるのを防ぐ。著者の教訓)。土台の改善は、それ以降に作るBOTにだけ効く
3. 自動テストを流す: (a) 過去30日の価格で動かして例外が出ない、(b) 入る条件が30日で1回以上成立する、(c) レバレッジ1倍・同時保有1・上限額・損切り・最長保有が守られている、(d) 生成部分にファイルの読み書き・外部通信・鍵の参照が含まれない(静的検査)
4. テストに落ちたら修理工程へ(5.7)。修理は通算3回まで

**出口**: paper評価へ

**判定**: `継続`(テスト中)/ `修理`(修理工程へ)/ `完了`

**1日の上限**: 5件(工場が回ったら10件に上げる候補。変更はボスの承認)

**AIの昇格条件**: 最初の14日で、「3回修理しても直らない」割合が実装件数の30%を超えたら、実装・修理のAIをSonnetからOpusに上げる(設定ファイルの1行変更)。これはダッシュボードに表示し、変更はボスの承認後にCommanderが指示する。

### 5.5 paper評価(試運転)

**入口**: 実装が完了したBOT

**処理**(AI不要):
1. 1回の上限額を**200ドル**として、実際の価格で「もし注文していたら」を記録する。実装が通った次の足から始める
2. 価格は3.1の「価格の受け取り口」から読む(BOTが取引所へ直接取りに行かない)
3. 毎日(run-daily)、開始時点から実際の価格でたどり直す。BOTが例外を出したら修理工程へ回す
4. **約定の決まり**(engine.py。早送り・本番と共用):
   - 入る: 条件が成立した足が閉じた時に判断し、**次の足の始値**で約定
   - 出る条件・保有の上限・利益確定: 成立した(利益確定は値段に触れた)足の**次の足の始値**で約定
   - 損切り: 触れた足の中で損切りの値段で約定。同じ足で利益確定にも触れたら損切りを先にする。窓を開けて損切りの値段を飛び越えて始まった足では、その始値で出る(不利な側に倒す)
   - 手数料(入り・出)、滑り(往復0.05%を入りと出に半分ずつ、不利な向き)、資金調達料(保有時間分)を必ず引く
5. 次の両方を満たすまで続ける: **14日以上** かつ **30回以上**の取引
6. 期間中に次のどれかに当たったら、その時点で不合格:
   - 連敗が8回に達した(札 `連敗`)
   - 最大の落ち込みが40ドル(200ドルの20%)を超えた(札 `落ち込み`)
   - 72時間、入る条件が一度も成立しなかった(札 `機会なし`)
7. 完走したら合格条件で判定(両型とも同じ):
   - 1取引あたりの平均純利益が**1ドル以上**
   - 利益の合計 ÷ 損失の合計 が**1.5以上**
   - 最大の落ち込みが**40ドル以内**
   - 連敗の最大が**8回未満**
   全部満たせば合格(判定 `仮説を支持`)。1つでも欠ければ不合格(それぞれ札 `利益不足` / `損益比不足` / `落ち込み` / `連敗`)

**出口**: 反証へ

**判定**: `待機`(開始前)/ `継続`(運転中)/ `保留`(データ欠損で一時停止)/ `完了`+`仮説を支持` / `見送り`

### 5.6 反証

**入口**: paper評価に合格したBOT

**処理**(計算はプログラム。AIはSonnetで「判定の説明文」を200字で書くだけ):
1. **前後半検査**: paper評価の期間を前半・後半に分け、両方の純利益がプラスか
2. **手数料2倍検査**: 手数料と滑りを2倍にして計算し直しても純利益がプラスか
3. **偏り検査**: 純利益の合計のうち、最大の1取引が占める割合が50%未満か
全部通れば合格。1つでも落ちれば否決(札 `前後半不一致` / `手数料2倍で赤字` / `一発依存`)

**出口**: 関所1(本番昇格待ち)へ

**判定**: `継続`(計算中)/ `見送り` / `完了`

### 5.7 修理

**入口**: 実装のテストに落ちたBOT、または本番・paper評価で例外(プログラムの異常終了)を起こしたBOT

**処理**(AI: Sonnet):
1. テスト結果と異常の内容を渡し、「入る条件」「出る条件」の部分だけ直させる。土台は触らせない
2. **軽い不具合(引数の渡し忘れ、型の違い、テスト用の設定不足など、売買ルールの意味を変えずに直せるもの)は、停止・裁定を求めず自力で直して進める**
3. 売買ルールの意味を変えないと直らない場合(AIが「直せない」と答えた場合を含む)は、直さずに否決(札 `実装不良`)。ルールの変更は新しい案として出し直す
4. 修理は通算3回まで(修理だけを数える)。3回で直らなければ否決(札 `実装不良`)

**出口**: 実装のテストへ戻る

**判定**: `継続` / `完了` / `見送り`

### 5.8 関所1: 本番昇格

**入口**: 反証に合格したBOT

**処理**:
1. ダッシュボードの「要判断」欄に表示し、同じ内容をメールで送る(内容: BOT記号、型、売買ルール、paper評価の成績、反証の結果、かかったAI代)
2. ボスが画面で「昇格」または「否決」を押す。否決の場合は理由を1行入れる(札 `ボス判断`)
3. 昇格したら資金段階1(50ドル)で本番運用へ

**ボスが判断するまで、工場は止まらない**(他の案は進み続ける)

### 5.9 本番運用

**入口**: 昇格したBOT

**資金の段階**:
| 段階 | 1回の上限額 | 次の段階に上がる条件 |
|---|---|---|
| 1 | 50ドル | 本番で14日以上・30回以上完走し、paper評価と同じ合格条件(1取引平均の基準は資金比で0.25ドル以上に読み替え)を満たす |
| 2 | 150ドル | 同上(平均の基準は0.75ドル以上) |
| 3 | 500ドル | 上限。これ以上は本書の範囲外 |

段階の繰り上げも**関所1と同じ手順**でボスが押す(1.6の「お金を入れる」に当たる)。

**自動停止の条件**(どれか1つで停止):
- その段階の資金の**20%**を失った(例: 段階1なら累計−10ドル)
- **72時間**、入る条件が成立しなかった
- 本番の最初の14日で、1取引あたりの平均純利益が**paper評価の半分以下**(注文が通らない・値段がずれる、を検出する規則。札 `本番乖離`)
- プログラムの異常終了(修理工程へ)

**関所2: 再開**: 停止したBOTは「要判断」欄に出る。ボスが「再開」「否決」を押す。再開は同じ段階から。

**全体の上限**: 本番運用中のBOTは同時に**10本まで**。本番に入れる資金の合計は**1,000ドルまで**。超える昇格候補は待機させる(ダッシュボードに表示)。

## 6. 否決メモ

### 6.1 定型(6項目のみ。長文にしない)
| 項目 | 内容 |
|---|---|
| メモID | 例 `M-00123` |
| 落ちた日 | |
| 工程 | 8工程のどれか、または `関所` |
| 型 | `値動き` / `歪み` |
| 札 | 6.2の一覧から1つ(複数不可。主因だけ) |
| 一言の理由 | 80字以内。数字を入れる(例: 「値幅0.4%に対し往復手数料0.09%+滑り0.05%で3倍未満」) |
| 案の要約 | 4.1の要約をそのまま写す(銘柄・場面・出方) |
| まとめ件数 | 6.3の用途3でまとめた時、元のメモの数(初期値1) |

### 6.2 札の一覧(固定。増やす時はボスの承認)
`重複` `手数料負け` `機会不足` `資金不足` `ルール不成立` `実装不良` `連敗` `落ち込み` `機会なし` `利益不足` `損益比不足` `前後半不一致` `手数料2倍で赤字` `一発依存` `本番乖離` `ボス判断` `未対応`

### 6.3 4つの用途(これ以外には使わない)
1. **登録前の照合**(探索の工程): 新しい仮説の「型+銘柄+入る条件の種類(7語: 高値抜け/安値割れ/平均回帰/急落/急騰/出来高急増/資金調達料)+数字(n=本数、x=%か倍率)」が、過去90日の**同じ型の**否決メモと一致し、かつ札が `手数料負け` `機会不足` `利益不足` `損益比不足` のどれかなら登録しない。一致の判定はAIを使わず、文字一致で行う
2. **設計時の注意書き**(新ロジック開発の1番): 同じ型・同じ銘柄・同じ出どころの否決メモを最大5件、AIに渡す
3. **週1回の棚卸し**(毎週月曜):
   - 直近7日の札を**型ごとに**数えて表にし、ダッシュボードに出す。数える時、`重複` と `合格` は除く
   - 最多の札に応じて探索・調査の絞り込みを自動で1段きつくする(例: 値動き型で `手数料負け` が最多なら、調査の「3倍未満」を「4倍未満」に。`機会不足` が最多なら「10回未満」を「15回未満」に。歪み型で `機会不足` が最多なら入口2の「3時間以上」を「6時間以上」に)。変更はログに残し、翌週に最多の札が変わったら元に戻す
   - **まとめ**: 案の要約が文字一致するメモが複数あれば1件にまとめ、「まとめ件数」に元の数を入れる(メモの重複を整理する。著者の「整理専門」に当たる)
4. **合格の記録**: 本番昇格したBOTも同じ定型で残す(札は `合格`。これだけ6.2の一覧外で使う)。昇格の基準を後で見直す材料にする

### 6.4 効いているかの測定(毎週)
ダッシュボードに次の3つを週ごと・型ごとに並べる。
- 照合で除外した仮説の数
- 案登録の数
- 本番昇格候補(反証合格)の数 ÷ 案登録の数(=合格率)

あわせて次の3つも出す(2026-10-25・ボス承認。著者の2026-10-24の記事で、作業の大半が「調べて記録しただけ」になり、知識の帳簿の多くが読まれていなかったため)。
- 調査で見送った数 ÷ 調査の結果が出た数(=見送り率。札 `未対応` は除く)。急に上がったら、探索の質が落ちたか、取れる機会が埋まってきたかを疑う
- 新ロジック開発で注意書きとしてAIに渡したメモの延べ数
- 一度もAIに渡されていないメモの数(`重複` と `合格` は除く)

「除外が増えているのに合格率が上がらない」なら、原因は探索の質にあると判断し、探索の絞り込み条件を見直す(Commanderが提案、ボスが決める)。

## 9. 安全の規則(変更にはボスの承認が必要)

- レバレッジ1倍固定。コードの土台に埋め込み、AIが生成する部分からは変更できない
- 同時保有1、1回の上限額は資金段階に従う。土台で強制
- **1本の資金の上限(資金段階の上限額)を超える案は、作っても動かさない**。新ロジック開発で上限額が段階の上限を超えたら、paper評価に進めず否決(札 `資金不足`)
- 損切りと最長保有時間は両型で必須。土台で強制
- 本番は同時10本・合計1,000ドルまで
- 注文の鍵は `.env` のみ。ログ・画面・AIへの送信文に鍵を含めない(送信前に検査)
- AIが生成したコードは、土台の決まった関数の中だけで動く。ファイルの読み書き・外部通信・鍵の参照を生成部分に書かせない(静的検査で弾く)
- BOTは1本ずつ自己完結。BOT同士で共通部品を参照しない。土台の更新は既存BOTに反映しない
- 本番の注文は、BOTごとに「1日の最大取引回数」を超えたら、その日は注文しない
- お金を入れる・鍵を渡す・有料契約は必ずボスが行う(1.6)
