## 0. 用語(初出の定義)

| 用語 | 意味 |
|---|---|
| BOT | 決められた売買ルールで自動で注文を出す小さなプログラム。本書では1本ごとに記号(例: B-0031)で呼ぶ |
| 案 | 「こういう場面で売買すれば儲かるかもしれない」という仮説。BOTになる前の状態 |
| 工場 | 案を出し、ふるいにかけ、合格したBOTだけ本番に出す一連の自動の流れ。本システム全体のこと |
| 工程 | 工場の中の段階。探索・調査・新ロジック開発・実装・paper評価・反証・修理・本番の8つ |
| paper評価(試運転) | お金を使わず、「もし動かしていたら」の損益だけを記録する試し運転 |
| 反証 | paper評価に合格したBOTを、別の角度から「本当に効いているか」を疑って検査する工程 |
| 否決メモ | 落ちた案・BOTについて「どの工程で・なぜ落ちたか」を定型で残す帳簿。本システムの要 |
| 札(タグ) | 否決メモに付ける分類ラベル。集計できるように、決まった語だけ使う |
| 関所 | ボスの判断を待って止まる場所。本番昇格(関所1)と本番再開(関所2)の2か所 |
| Hyperliquid | 本システムが取引する暗号資産の取引所。無期限先物(期限のない先物)を扱う。取引記録が全員分公開されている |
| 財布(ウォレット) | Hyperliquid上の口座にあたるもの。住所(アドレス)という文字列で識別する |
| 順位表 | Hyperliquidが公開している、成績上位の財布の一覧 |
| 資金調達料 | 無期限先物を持ち続ける人が一定時間ごとに払う(または受け取る)手数料 |
| 手数料 | 注文1回ごとに取引所に払う費用 |
| AI窓口 | 工場の中でAIに質問を送る唯一の口。ここの設定を変えるだけで、使うAI(Claude Code / API)を切り替えられる |
| API | 使った分だけ払う方式でAIを呼ぶ接続口。Claude Code(Max契約)とは別の口座 |
| Haiku / Sonnet / Opus | Claude(AI)の3段階。Haikuが最も安く速い、Opusが最も高く賢い、Sonnetは中間 |
| レバレッジ | 手持ち資金より大きな金額で取引する仕組み。本システムは**1倍固定**(使わない) |
| ダッシュボード | 工場の状態を見る画面。手元のパソコンのブラウザで開く |

## 1. 目的と方針

### 1.1 目的
「儲かる可能性が高いBOTを、人手をかけずに探し続ける工場」を自分の手元に持つこと。

### 1.2 「儲かる」の定義(ボスの見解を採用)
検証(paper評価と反証)に合格し、**本番で実際に利益が出た結果**だけを「儲かった」と呼ぶ。試運転の数字や推定は「儲かりそう」であり、「儲かった」ではない。

### 1.3 最初の目標(利益ではない)
最初の2〜3か月の目標は次の3つ。本番の利益はこの期間の目標に含めない。
1. 工場が毎日、人手なしで一周する(探索から反証まで自動で進む)
2. 否決メモが育ち、同じ理由で落ちる案が減っていることが数字で見える
3. 本番昇格の候補が、ボスの前に定期的に(週に数件以内で)届く

### 1.4 著者(あいかわひびき氏)の方式との違い
参考にしたのは「AIにBOTを量産させ、試運転で選別し、本番に出す」という工場の形と、否決の経験をwikiに溜める考え方。本システムで変えた点は次の5つ。
1. 否決メモに札を付け、集計できる帳簿にする(著者は2,500ページの読み物)
2. 新しい案を登録する前に否決メモと照合し、同じ理由で落ちた案は出さない
3. 探索の入口に「儲けている財布の分析」を置く
4. BOTごとにかかったAI代を帳簿に付け、利益と並べる
5. 「反証」を正式な工程にする

### 1.5 やらないこと(禁止)
- BOT・コード・シグナルを他人に売る、貸す、配信する
- 他人の資金を預かって運用する
- レバレッジを使う(常に1倍)
- 記事の文章・画像を転載する
(理由: 自分の資金で自分用に動かす限り、著作権・取引所規約・金融の法律のいずれにも触れない。売る・貸す・預かる・配信するは金融商品取引業の登録対象で、無登録は刑事罰。本書の範囲外とする)

## 2. 全体像

### 2.1 工程の流れ

```
探索 → 調査 → 新ロジック開発 → 実装 → paper評価 → 反証 → [関所1: 本番昇格] → 本番運用 → (自動停止) → [関所2: 再開]
                                   ↑         ↓(不具合)
                                   └── 修理 ──┘
各工程で落ちたものは → 否決メモ へ
```

たとえ: 包丁工場。「名人の包丁を1本盗む」のではなく「毎日たくさん作って、試食会と検査に通ったものだけ店に出す」。ボスが押すのは「出荷の判子(関所1)」と「ライン再開の判子(関所2)」だけ。

### 2.2 各工程の役目(1行ずつ)

| 工程 | 役目 | 使うAI |
|---|---|---|
| 探索 | 儲けている財布を見つけ、その取引の癖から案を出す | Haiku |
| 調査 | 案が「手数料で消えないか」「資金で足りるか」を調べて見送り/継続を決める | Haiku |
| 新ロジック開発 | 案を、数字で書いた売買ルールに落とす | Sonnet |
| 実装 | 売買ルールからBOTのコードとテストを書く | Sonnet |
| paper評価 | 14日以上・30回以上の試運転で成績を記録し、合格条件で判定 | AI不要(計算のみ) |
| 反証 | 合格したBOTを「たまたまではないか」の3条件で検査 | Sonnet(判定の説明文のみ) |
| 修理 | 実装不良・軽い不具合を直す。3回で直らなければ落とす | Sonnet |
| 本番運用 | 本番資金で動かす。停止条件で自動停止 | AI不要 |

### 2.3 案の残り方の目安(100件あたり・推定)

| 工程 | 残る数 |
|---|---|
| 探索で案登録 | 100 |
| 調査を通過 | 30〜40 |
| 実装まで進む | 15〜20 |
| paper評価を完走 | 10〜15 |
| 反証を通過 | 3〜5 |
| 本番昇格 | 1〜10 |

最初は1%、否決メモが育てば10%が目安。これは目標であり、合格条件を緩めて達成してはならない。

## 5. 工程ごとの仕様

各工程は「入口(何を受け取るか)→処理→出口(どこへ送るか)→判定(どの札か)」で書く。

### 5.1 探索

**入口**: なし(毎日自動で始まる)

**処理**(財布分析方式):
1. Hyperliquidの順位表から、直近30日の成績上位の財布を最大300件取る(AI不要)
2. 各財布の直近30日の取引履歴を、1件ずつ読み取り窓口で取る(AI不要)
3. 次の条件で絞る(AI不要):
   - 取引回数が30日で50回以上
   - 30日の純利益がプラス
   - 最大の落ち込み(一時的に資金が減った最大幅)が20%以内
   - **独自条件**: 1回あたりの取引額の中央値が2,000ドル以下(資金50〜500ドルで真似できる取引をしている人を優先)
4. 絞った財布は最大30件。各財布について、**ここで初めてAI(Haiku)**に次を頼む:
   「この財布の直近100件の取引(銘柄・入った時刻と価格・出た時刻と価格)を読み、どんな場面で入り、どんな場面で出ているかの仮説を3つ、各300字以内で書け。銘柄・時間の単位・入る条件・出る条件を必ず含めること」
5. 出てきた仮説(最大90件/日)を**登録前照合**にかける(6.3)。似た否決メモがあれば登録しない
6. 残った仮説を案として登録(判定: 案登録)
7. 同じ財布は7日間は再分析しない

**出口**: 調査工程へ

**判定の札**: `案登録` / `照合で除外`(除外は否決メモに札 `重複` で残す)

**費用の上限**: 1日あたりHaikuの入力500万文字分まで。超えたらその日は打ち切り

**将来の2本目の入口(本書では作らない)**: 市場のゆがみ(先物と現物の価格差、資金調達料が極端な銘柄)を毎日計算して案にする方式。工場が回ってから別途仕様化する。

### 5.2 調査

**入口**: 案登録された案

**処理**(AI: Haiku。ただし数字の計算はプログラムで行い、AIには「見送りの理由の文章化」だけ頼む):
1. 想定の値幅(入る条件から出る条件までの差)が、往復の手数料+想定の滑り(注文が思った値段で通らない分。0.05%固定)の**3倍未満**なら見送り(札 `手数料負け`)
2. その銘柄の直近30日で、入る条件に当てはまる場面が**10回未満**なら見送り(札 `機会不足`)
3. 必要資金が200ドルを超える条件(例: 最小注文単位が大きい銘柄)なら見送り(札 `資金不足`)
4. 上記を通ったら継続

**出口**: 新ロジック開発へ

**判定**: `継続` / `見送り` / `保留`(外部データが取れなかった時。翌日再試行、3回で `未対応` として否決)

### 5.3 新ロジック開発

**入口**: 調査を通った案

**処理**(AI: Sonnet):
1. 否決メモから、この案と同じ銘柄・同じ出どころで落ちたメモを最大5件取り、「過去にこの理由で落ちている」としてAIに渡す(6.3の用途2)
2. AIに、4.2の定型に沿った売買ルールを**1つだけ**書かせる。定型にない項目は書かせない
3. 定型の全項目が数字で埋まっているかをプログラムで検査。欠けていれば1回だけ書き直し。それでも欠ければ否決(札 `ルール不成立`)

**出口**: 実装へ

**判定**: `完了` / `developed`は使わない(完了に統一)/ `保留`(書き直し待ち)

### 5.4 実装

**入口**: 売買ルール

**処理**(AI: Sonnet):
1. 共通の土台(`bots/_template/`)をコピーし、売買ルールの「入る条件」「出る条件」の部分だけをAIに書かせる。注文・記録・停止の部分は土台で固定し、AIに触らせない
2. 自動テストを流す: (a) 過去30日の価格で動かして例外が出ない、(b) 入る条件が30日で1回以上成立する、(c) レバレッジ1倍・同時保有1・上限額が守られている
3. テストに落ちたら修理工程へ(5.7)。修理は通算3回まで

**出口**: paper評価へ

**判定**: `継続`(テスト中)/ `修理`(修理工程へ)/ `完了`

**AIの昇格条件**: 最初の14日で、「3回修理しても直らない」割合が実装件数の30%を超えたら、実装・修理のAIをSonnetからOpusに上げる(設定ファイルの1行変更)。これはダッシュボードに表示し、変更はボスの承認後にCommanderが指示する。

### 5.5 paper評価(試運転)

**入口**: 実装が完了したBOT

**処理**(AI不要):
1. 1回の上限額を**200ドル**として、実際の価格で「もし注文していたら」を記録する
2. 手数料は実際の料率で、資金調達料は保有時間分を、必ず引く
3. 次の両方を満たすまで続ける: **14日以上** かつ **30回以上**の取引
4. 期間中に次のどれかに当たったら、その時点で不合格:
   - 連敗が8回に達した(札 `連敗`)
   - 最大の落ち込みが40ドル(200ドルの20%)を超えた(札 `落ち込み`)
   - 72時間、入る条件が一度も成立しなかった(札 `機会なし`)
5. 完走したら合格条件で判定:
   - 1取引あたりの平均純利益が**1ドル以上**
   - 利益の合計 ÷ 損失の合計 が**1.5以上**
   - 最大の落ち込みが**40ドル以内**
   - 連敗の最大が**8回未満**
   全部満たせば合格(判定 `仮説を支持`)。1つでも欠ければ不合格(それぞれ札 `利益不足` / `損益比不足` / `落ち込み` / `連敗`)

**出口**: 反証へ

**判定**: `待機`(開始前)/ `継続`(運転中)/ `保留`(データ欠損で一時停止)/ `完了`+`仮説を支持` / `見送り`

### 5.6 反証

**入口**: paper評価に合格したBOT

**処理**(計算はプログラム。AIはSonnetで「判定の説明文」を200字で書くだけ):
1. **前後半検査**: paper評価の期間を前半・後半に分け、両方の純利益がプラスか
2. **手数料2倍検査**: 手数料を2倍にして計算し直しても純利益がプラスか
3. **偏り検査**: 純利益の合計のうち、最大の1取引が占める割合が50%未満か
全部通れば合格。1つでも落ちれば否決(札 `前後半不一致` / `手数料2倍で赤字` / `一発依存`)

**出口**: 関所1(本番昇格待ち)へ

**判定**: `継続`(計算中)/ `probe`は使わない / `見送り` / `完了`

### 5.7 修理

**入口**: 実装のテストに落ちたBOT、または本番・paper評価で例外(プログラムの異常終了)を起こしたBOT

**処理**(AI: Sonnet):
1. テスト結果と異常の内容を渡し、「入る条件」「出る条件」の部分だけ直させる。土台は触らせない
2. **軽い不具合(引数の渡し忘れ、型の違い、テスト用の設定不足など、売買ルールの意味を変えずに直せるもの)は、停止・裁定を求めず自力で直して進める**
3. 売買ルールの意味を変えないと直らない場合は、直さずに否決(札 `実装不良`)。ルールの変更は新しい案として出し直す
4. 修理は通算3回まで。3回で直らなければ否決(札 `実装不良`)

**出口**: 実装のテストへ戻る

**判定**: `継続` / `完了` / `見送り`

### 5.8 関所1: 本番昇格

**入口**: 反証に合格したBOT

**処理**:
1. ダッシュボードの「要判断」欄に表示し、同じ内容をメールで送る(内容: BOT記号、売買ルール、paper評価の成績、反証の結果、かかったAI代)
2. ボスが画面で「昇格」または「否決」を押す。否決の場合は理由を1行入れる(札 `ボス判断`)
3. 昇格したら資金段階1(50ドル)で本番運用へ

**ボスが判断するまで、工場は止まらない**(他の案は進み続ける)

### 5.9 本番運用

**入口**: 昇格したBOT

**資金の段階**:
| 段階 | 1回の上限額 | 次の段階に上がる条件 |
|---|---|---|
| 1 | 50ドル | 本番で14日以上・30回以上完走し、paper評価と同じ合格条件(1取引平均の基準は資金比で0.25ドル以上に読み替え)を満たす |
| 2 | 150ドル | 同上(平均の基準は0.75ドル以上) |
| 3 | 500ドル | 上限。これ以上は本書の範囲外 |

段階の繰り上げも**関所1と同じ手順**でボスが押す。

**自動停止の条件**(どれか1つで停止):
- その段階の資金の**20%**を失った(例: 段階1なら累計−10ドル)
- **72時間**、入る条件が成立しなかった
- 本番の最初の14日で、1取引あたりの平均純利益が**paper評価の半分以下**(注文が通らない・値段がずれる、を検出する規則)
- プログラムの異常終了(修理工程へ)

**関所2: 再開**: 停止したBOTは「要判断」欄に出る。ボスが「再開」「否決」を押す。再開は同じ段階から。

**全体の上限**: 本番運用中のBOTは同時に**10本まで**。本番に入れる資金の合計は**1,000ドルまで**。超える昇格候補は待機させる(ダッシュボードに表示)。

## 6. 否決メモ

### 6.1 定型(5項目のみ。長文にしない)
| 項目 | 内容 |
|---|---|
| メモID | 例 `M-00123` |
| 落ちた日 | |
| 工程 | 8工程のどれか、または `関所` |
| 札 | 6.2の一覧から1つ(複数不可。主因だけ) |
| 一言の理由 | 80字以内。数字を入れる(例: 「値幅0.4%に対し往復手数料0.14%+滑り0.1%で3倍未満」) |
| 案の要約 | 4.1の要約をそのまま写す(銘柄・場面・出方) |

### 6.2 札の一覧(固定。増やす時はボスの承認)
`重複` `手数料負け` `機会不足` `資金不足` `ルール不成立` `実装不良` `連敗` `落ち込み` `機会なし` `利益不足` `損益比不足` `前後半不一致` `手数料2倍で赤字` `一発依存` `本番乖離`(本番がpaperの半分以下) `ボス判断` `未対応`

### 6.3 4つの用途(これ以外には使わない)
1. **登録前の照合**(探索の5番): 新しい仮説の「銘柄+時間の単位+入る条件の種類(例: 高値抜け/平均回帰/資金調達料)」が、過去90日の否決メモと一致し、かつ札が `手数料負け` `機会不足` `利益不足` `損益比不足` のどれかなら登録しない。一致の判定はAIを使わず、上記3項目の文字一致で行う
2. **設計時の注意書き**(新ロジック開発の1番): 同じ銘柄・同じ出どころの否決メモを最大5件、AIに渡す
3. **週1回の棚卸し**: 毎週月曜に、直近7日の札を数えて表にし、ダッシュボードに出す。最多の札に応じて探索の絞り込みを自動で1段きつくする(例: `手数料負け` が最多なら、調査の「3倍未満」を「4倍未満」に。`機会不足` が最多なら「10回未満」を「15回未満」に)。変更はログに残し、翌週に最多の札が変わったら元に戻す
4. **合格の記録**: 本番昇格したBOTも同じ定型で残す(札は `合格`。これだけ6.2の一覧外で使う)。昇格の基準を後で見直す材料にする

### 6.4 効いているかの測定(毎週)
ダッシュボードに次の3つを週ごとに並べる。
- 照合で除外した仮説の数
- 案登録の数
- 本番昇格候補(反証合格)の数 ÷ 案登録の数(=合格率)

「除外が増えているのに合格率が上がらない」なら、原因は探索の質にあると判断し、探索の絞り込み条件を見直す(Commanderが提案、ボスが決める)。

## 9. 安全の規則(変更にはボスの承認が必要)

- レバレッジ1倍固定。コードの土台に埋め込み、AIが生成する部分からは変更できない
- 同時保有1、1回の上限額は資金段階に従う。土台で強制
- 本番は同時10本・合計1,000ドルまで
- 注文の鍵は `.env` のみ。ログ・画面・AIへの送信文に鍵を含めない(送信前に検査)
- AIが生成したコードは、土台の決まった関数の中だけで動く。ファイルの読み書き・外部通信を生成部分に書かせない(静的検査で弾く)
- 本番の注文は、BOTごとに「1日の最大取引回数」を超えたら、その日は注文しない
