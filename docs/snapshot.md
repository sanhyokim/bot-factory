## 段階3の確認中に直したこと(2026-10-20)

- 1日目(10/20 手動)の結果: 順位表の300財布がすべて絞り込みで落ち、案は0件(取引回数が足りない 168、約定が多すぎる 132)。調査は見本の10件を「未対応」で否決(否決メモ+10)
- 取引回数の数え方を、約定ごとに取引所が返す「約定の直前の保有」に合わせ直す形にした(同じ時刻の約定の順の前後や欠けた約定で数え違えないため)。ただし診断では前の数え方でもずれは0件で、1日目に落ちた原因ではなかった
- 数え方を直したので、前の数え方で調べた財布は7日を待たずに調べ直す(wallet_scans に数え方の版を持たせた)
- 財布を読んでいる間、50財布ごとに進み具合を出す(読み終わるまで1時間以上かかり、その間なにも出なかったため)
- 開発用に `python -m factory explore-check` を足した。run-daily と同じ順に候補の財布を少し読み、絞り込みの条件ごとに何件満たすかを出す(記録は残さない)
- 本当の原因(10/20 の診断): 順位表の損益の上位は、資金数百万〜数億ドルの財布(約定6000件超の高頻度の取引、または30日でほとんど手仕舞いしない)ばかりで、取引額の中央値2000ドル以下の財布が1件もなかった。利益率の上位も、入出金で利益率がゆがんだ財布や取引額の大きい財布だった
- 探索の候補の選び方を決めた(仕様5.1の1は「成績上位を最大300件」としか書いていないため): 順位表のうち、30日の損益がプラスで、資金が100〜1万ドル、30日の取引量が1万〜300万ドル、30日前の資金(今の資金 − 30日の損益)がプラスの財布を候補にし、損益の順に並べる。1日に最大300件を調べ、7日以内に調べた財布は飛ばして次の財布へ進む(config.yaml の explore.candidate_account_usd・candidate_volume_usd)。絞り込みの数字(50回・プラス・20%・2000ドル・6000件・30財布)は変えていない
- 2026-10-21 の診断: 資金と取引量の下限だけで絞った候補(805財布)でも、損益の上位30件はすべて「30日の損益が今の資金より大きい」財布(資金数千ドルで損益数万〜28万ドル。利益を引き出しながら数百万ドル単位で張る)で、通過は0件だった。そこで取引量の上限(300万ドル。取引額2000ドルで750回の往復分)と「30日前の資金がプラス」を候補の条件に足した。後者は、落ち込みの計算(5.1の3)が30日前の資金を同じ式で推すため、その推定が成り立つ財布に限る意味もある

## 指示書A(2026-10-20)で変えたこと

- 入る条件の種類は7語(高値抜け / 安値割れ / 平均回帰 / 急落 / 急騰 / 出来高急増 / 資金調達料)だけ。「その他」は照合キーから外した
- 探索で7語のどれにも分類できない仮説は案として登録せず、否決メモだけ残す(工程=探索、札=ルール不成立、理由「入る条件の種類を分類できず」)。AIには7語か「分類できない」を選ばせる
- 以前に「その他」で登録された案は、run-daily の最初(前回の一括処理の受け取りの前)に同じ札・同じ理由で否決する。試運転中のBOTがあれば否決にする
- 調査の「その他は場面の数を飛ばす」分岐は削除した。7語でない案が調査に来たら札「ルール不成立」で否決する
- paper評価の約定の値段(項目3):
  - 入る: 条件が成立した足が閉じたら、次の足の始値で約定
  - 出る条件・保有の上限・利益確定: 成立(利益確定は値段に届いた)した足の次の足の始値で約定
  - 損切り: 届いた足の中で、損切りの値段で約定。同じ足で利益確定にも届いたら損切りを先にする。入った次の足以降に、窓を開けて損切りの値段を飛び越えて始まった時は、その始値で約定(不利な側に倒す。段階2からの決まりをそのまま残した)
  - 滑り: 往復0.05%(config.yaml の hyperliquid.slippage_pct。調査の計算と同じ値)を、入りと出に半分ずつ、不利な向きに約定の値段へ含める。数量は滑りを含めた入りの値段で計算する
  - 手数料(入り・出の両方、0.045%)と資金調達料は従来どおり
  - 反証の計算と合格条件の数字は変えていない
- 試運転中のBOTは、run-daily が毎日 paper評価の開始時刻から今までをたどり直すので、次の run-daily で新しい決まりで計算し直される

## 段階2で実装役が決めたこと

- BOT 1本 = `bots/<名前>/` に `bot.yaml`(銘柄・時間の単位・利益確定%・損切り%・1日の最大取引回数)と `strategy.py`(`entry_signal` と任意の `exit_signal` だけ)。土台本体は `factory/engine.py`・`botbase.py`・`autotest.py`
- strategy.py の静的検査: import は math と statistics だけ。open・eval・getattr などの名前、`_` で始まる属性、class・try・with・global は不可。一番外側は import・関数・定数だけ
- 約定の決まり: 判断は足が閉じた時、注文は次の足の始値。利益確定・損切りは足の中で届いた値段で約定。同じ足で両方に届いたら損切りを先にする(不利な側)。窓を開けて飛び越えたら始値で約定(→ 指示書A 項目3で利益確定は次の足の始値に変更。上の「指示書Aで変えたこと」)
- 手数料: 入り・出の両方を成行の料率 0.045%(Hyperliquidの最も下の段階)で計算。滑りはpaper評価では引かなかった(SPEC 5.5に記載がないため。→ 指示書A 項目3で約定の値段に含めるよう変更)
- 資金調達料: 持っている間の毎時の率 × 数量 × その時刻の足の終値。買いはプラスの率で払い、売りは受け取る
- 数量は取引所の小数桁で切り捨て。10ドル未満の注文は出さない。期間の終わりに持っている取引は数えない
- 落ち込みは、決着した取引の累計損益の最高値からの下げ幅(ドル)
- 完走の時点は「14日経過」と「30回目の決着」の遅い方。その後の取引は判定に使わない
- 「72時間、入る条件が成立しない」は、持っている間の成立も成立として数える
- 反証の前後半は、評価期間の真ん中の時刻で分け、取引は決着した時刻で振り分ける。純利益の合計がマイナスなら偏り検査も不合格
- 反証の説明文(Sonnet・200字)は `refute.explain()` として用意し、早送りでは呼ばない(段階3で工程に組み込む)
- 早送り(`paper-ff`)は記録をデータベースに書かない。不合格・未完走でも反証の3検査を「参考」として表示する

## 段階3で実装役が決めたこと

- run-daily の順番: 週1回の棚卸し → 前回の一括処理(AI)の受け取り → paper評価・反証 → 探索 → 調査 → 新ロジック開発 → 実装・修理。工程ごとに失敗しても残りは続け、結果は `data/logs/run-daily-日付.log` に残す
- 案登録から paper評価の開始までは1回の実行で進む。paper評価は実時間で14日以上かかるので、反証に届くのは早くても開始から14日後。「3日連続で流す」確認では、案が paper評価中まで自動で進み、否決メモが自動で増えることを見る。反証から関所1までの流れは、テスト(偽の取引所・偽のAI)で確かめた
- 価格は `candles`・`funding` の表に貯める(取引所は直近5000本しか返さず、5分足だと約17日分しかないため)。閉じた足だけ保管し、足りない分だけ取りに行く
- 取引所の読み取りは1分あたりの重さを1000までに抑える(取引所の上限は1200)
- 探索の絞り込み: 取引回数は「入ってから出るまで」を1回として数える(約定から組み立てる。期間の前から持っていた分は数えない)。落ち込みは確定した損益の資金曲線で計り、30日前の資金は「今の資金−30日の損益」で推定する。取引額の中央値は1回の取引の最大保有額で計る。無期限先物以外(現物など)の約定は除く
- 約定が6000件を超える財布(高頻度の取引)は読み切らずに対象外とする。調べた財布はすべて7日間は再分析しない
- 探索のAIには、入る条件の種類を次の語から選ばせる(照合キーにもそのまま使う): 高値抜け / 安値割れ / 平均回帰 / 急落 / 急騰 / 出来高急増 / 資金調達料(指示書Aで「その他」を外した。どれでもなければ「分類できない」を選ばせ、登録しない)。数字は n(本数)と x(% か倍率)の2つ、向きは買い/売り
- 仮説は「答えの形」(JSON)を決めて受け取り、数字が読めない仮説は捨てる。探索のAIは一括処理(半額)で送り、最大30分待つ。間に合わなければ次の実行で受け取る
- 調査の「想定の滑り0.05%」は往復で1回分として計算する: 3 ×(手数料0.045%×2 + 0.05%)= 0.42%。値幅は利益確定の%。滑りの値は config.yaml の hyperliquid.slippage_pct(paper評価の約定と共用)
- 調査の「入る条件に当てはまる場面」は、条件が成り立ち始めた回数(続いている間は1回)。1分・5分足で30日分が取れない時は、取れた日数から30日分に換算する
- 調査で取引所にない銘柄・数字のない案(段階1で手で入れた見本の10件など)は、札「未対応」で否決する
- 調査の見送りの理由は、まずプログラムが数字入りで書き、Haikuに一括処理で言い換えさせて次の実行で差し替える(SPEC 5.2「AIには文章化だけ」)。AIが使えない時はプログラムの文のまま
- 週1回の棚卸しは、今週(月曜始まり)にまだ行っていなければ実行する。最多の札を選ぶ時、「重複」(照合で除外できた印)と「合格」は数えない。手数料負け→3倍を4倍に、機会不足→10回を15回に。翌週に最多の札が変われば元に戻す
- 新ロジック開発: 売買ルールの利益確定・損切りの%は数字の列(rules.take_profit_pct / stop_loss_pct)にも持つ。検査は「全項目が数字で埋まっているか・入る条件に買い/売りの向きがあるか・銘柄が案と同じか」
- 実装: AIが書くのは strategy.py だけ。bot.yaml はルールからプログラムが作る。修理の回数(bots.attempts)は修理だけを数える(最初の実装は0回目)。修理で「直せない」と答えた時(ルールの意味を変えないと直らない)も札「実装不良」
- 実装・修理で落ちたBOTも bots に「否決」で残す(画面の「修理しても直らなかった割合」(SPEC 5.4)に使う)
- paper評価は、実装が通った次の足から始める。毎日、開始時刻から今までの実際の価格でたどり直し、取引記録を置き換える。開始前の300本は判断の材料として見せるだけで売買しない。データが欠けた日は保留にして翌日やり直す。BOTが例外を起こしたら修理に回す
- BOTの土台に `history.funding_rates(n)`(その足が閉じた時点までに決まった資金調達料)を足した。資金調達料を使う案のため
- 1日の上限: 調査90件、新ロジック開発10件、実装5件(config.yaml)
- 画面に枠4(paper評価中)と枠6(費用: 工程ごとの今月の費用・案/BOTごとの上位10件・クレジット残高の見込み・修理しても直らなかった割合)を足した。枠3(本番運用中)は段階4で足す
- 毎日の自動実行は、Windowsのタスクスケジューラに `run-daily.cmd` を登録する(電源が切れていた日は、次に電源を入れた時に動く)
